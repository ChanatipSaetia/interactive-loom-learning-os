**Topic:** Unified OKF Loading Pipeline — Removing YAML Parsing from the Composition Engine
**Date:** 2026-09-27

---

## Context

`docs/agents/domain.md` forbids the Composition Engine from parsing raw YAML, but three independent parse/assemble paths exist today and have drifted:

| Path | File | Behavior |
|---|---|---|
| Lesson stream (browser) | `src/core/learning-engine/composition/okf/reader.ts` | `js-yaml` + ~400 lines of hand-written `map*` normalizers; never calls the gateway; file membership from `index.yaml` `related:` |
| CLI / CI | `scripts/validate-okf.ts` | Own multi-file assembly via `fs.readdirSync` (sees stale files, alphabetical order); calls the gateway |
| Authoring editor | `supporting/authoring-editor/hooks/useSectionEditorBuffer.ts` | Single-string `validateOKFSection` |

Additional defects found: `OKFStoragePort.readSection` returns parsed data, causing a `reader.ts` ↔ `in-repo-storage.ts` import cycle (`reader.ts:751`); `bundleToSections` is a fourth transform layer; `deriveSchema` is deep-imported from `components/` in three places; the deploy workflow does not run `okf:validate`.

---

## Q1: Gateway Output Shape

**Q:** Should the Validation Gateway output the on-disk authoring shape (with per-sub-context mappers) or a render-ready shape?

**A:** Option A: Zod schemas `.transform()` to the render shape. The gateway output is render-ready; `z.input` / `z.output` provide both types.

**Decision:** Each sub-context `schema.ts` owns parsing *and* normalization via Zod transforms. The `map*` functions in `reader.ts` are deleted. Tier 3 validates the output shape.


## Q2: Writing the Render Shape Back to Disk

**Q:** Zod transforms are one-way. How does the editor serialize back to disk?

**A:** Out of scope for this refactor.

**Decision:** Parked. See *Parked Risks*.


## Q3: Multi-File Section Assembly

**Q:** Who knows which files compose a section (e.g. flowchart = `actors.yaml` + `systems.yaml` + `steps.yaml` + `journeys.yaml`)?

**A:** Option A: The sub-context declares a `SectionLayout`; the gateway assembles.

**Decision:** Each sub-context exports a `SectionLayout` with two modes — `collection` (one item per file, `resource: .`) and `single` (one array file, `resource: x.yaml`) — plus fixed-name files. New gateway entry point `validateSectionFiles({ meta, files: Record<filename, string> })` runs Tier 1 per file (diagnostics name `steps.yaml:14`), assembles, then Tier 2/3. Reader, CLI, and embed adapter all call it.


## Q4: Source of Truth for Collection File Membership

**Q:** Hand-maintained `index.yaml` `related:`, the filesystem, or a per-section `resources:` list?

**A:** Option B: The filesystem is the source of truth; a generated manifest serves the browser.

**Decision:** Directory contents define section membership. Stale files (`motorcycle/sections/taxonomy/-drivetrain.yaml`, `-engine-system.yaml`) must be deleted before cut-over. `related:` is retired.


## Q5: Ordering Under Filesystem Truth

**Q:** ~22 of 27 collection sections use a deliberate non-alphabetical `related:` order. How is order expressed?

**A:** Option A: Numeric filename prefixes (`01-mesopotamia.yaml`).

**Decision:** Filesystem sort order = render order. Migration script derives prefixes from current `related:` order. Safe because item IDs come from the `id:` field, and hexmaps reference section folders, not files.


## Q6: Generated Manifest Location & Lifecycle

**Q:** Commit the manifest (like `public/index.yaml`), generate it uncommitted, or commit + CI drift check?

**A:** Option B: Generated, never committed.

**Decision:** Extend `okf-save-plugin` in `vite.config.ts`: dev middleware serves `/okf/<topic>/manifest.json` computed live from disk; build emits it into `dist/`. The CLI reads `fs` directly. Assumes no one hosts raw OKF folders for `loom-sections` outside this build.


## Q7: Runtime Policy for Sections with `status: error`

**Q:** Placeholder, skip, or fail the whole topic?

**A:** Option A + CI gate.

**Decision:** An `error` section keeps its slot and renders a placeholder card — full diagnostics (tier, `file:line`, `fixHint`) in dev, a minimal notice in prod. Sections load via `Promise.allSettled`, so hexmap `sectionRef` and learner-progress `sectionId` keys always resolve. `warning` renders normally with a dev-only badge. `npm run okf:validate` is added to `deploy-gh-pages.yml` before `build` and blocks deploys.


## Q8: Alias / Tolerant Reading

**Q:** Carry `reader.ts` alias handling (array vs dict actors, `label`/`role`, uppercase `AGGREGATE`, wrapped files…) into the schemas, or go strict?

**A:** Option A: Strict canonical schemas.

**Decision:** Measured usage: every flowchart alias branch has 0 users across 23 flowcharts. Only 3 outlier files use wrapped forms (1 `steps.yaml`, 1 `questions.yaml`, 1 `glossary.yaml`); migrate them and delete all alias branches. The dead `entities`/`relations`/`views` branch of `FlowchartSectionSchema` is removed too. Non-canonical content surfaces as Tier 2 diagnostics with `fixHint`.


## Q9: Storage Port Altitude

**Q:** Should `OKFStoragePort` return parsed data or raw files?

**A:** Option A: Raw files only.

**Decision:**
```ts
interface OKFStoragePort {
  listSections(topicId): Promise<string[]>
  readSectionFiles(topicId, folder): Promise<Record<string, string>>
  readHexMap(topicId): Promise<string>
}
```
A `loadSection(storage, topicId, folder)` use case in `composition/okf/` orchestrates storage → `validateSectionFiles` → `ValidationResult`. Adapters never import composition, eliminating the cycle. The adapter is constructed at the app entry and injected via a provider; the `inRepoStorage` module singleton is removed. `scripts/validate-okf.ts` uses a new `NodeFsStorageAdapter` and drops its assembly logic.


## Q10: Flowchart Derivation & `bundleToSections`

**Q:** Where does `AbstractFlow` → `UnifiedFlowchartSchema` derivation happen, and does `bundleToSections` survive?

**A:** Option A: Payload is the domain model; the component derives.

**Decision:** Gateway output for flowchart is `{ type, flow: AbstractFlow }`. `<Flowchart flow>` calls `deriveSchema` in `useMemo`. Payload maps 1:1 to props (`{ type, props: { ...metaProps, ...payload } }`, typed via `SectionPropsMap[type] = z.output<Schema>`); `bundleToSections` is deleted. `abstract-flow/` (types + `derive.ts`) moves from `components/flowchart/` to `process-simulation/model/` and is exported from the sub-context `index.ts`.


## Q11: Rollout & Verification

**Q:** Parity snapshots, big-bang PR, or per-type strangler flag?

**A:** Option A: Parity snapshots first.

**Decision:** Four mechanically verified steps — snapshot, migrate content (old reader must still match), build new pipeline (must match snapshots), delete old code.

## Summary of Decisions

- **Single pipeline (Q1, Q3, Q9):** `OKFStoragePort` (raw files) → `loadSection` use case → `validateSectionFiles` (per-file Tier 1, `SectionLayout` assembly, transforming Zod Tier 2, Tier 3 on output) → `ValidationResult`. Browser, CLI, and embed share it.
- **File membership (Q4, Q5, Q6):** Filesystem is truth; numeric filename prefixes define order; manifest generated by the Vite plugin, never committed.
- **Strictness (Q8):** Canonical-only schemas; 3 outlier files migrated; all alias branches deleted.
- **Runtime resilience (Q7):** Per-section isolation with placeholder slots; `okf:validate` gates deploys.
- **Props mapping (Q10):** Payload = props; `bundleToSections` deleted; `AbstractFlow` is the flowchart domain model and components derive views.
- **Rollout (Q11):** Snapshot-parity driven.

## Parked Risks

- **Editor round-trip (Q2):** The editor's `lastValidData` becomes the transform output, and save uses `yaml.dump(output)`. For multi-file sections (flowchart) this writes a single `flow:` blob instead of four files. Needs a per-sub-context `serialize(output) → Record<filename, string>` (canonical-on-save) before the editor is migrated.
- **Gamification composition root:** `useGamification.ts:6` instantiates `InRepoStorageAdapter` directly; should consume the same injected provider.
- **Raw-folder hosting (Q6):** If OKF folders are ever served to `loom-sections` without a Vite build, the manifest will be missing; the CLI could emit it on demand.

## Implementation Notes

Decisions made while implementing, where the code needed more detail than the log above:

- **Idempotent schemas.** Every section schema's output is valid input (e.g. flowchart refs accept `"id"` or `{ id }` and emit `{ _tag: 'ref', id }`), so the editor's re-validation of render-shaped data keeps working without a separate input path.
- **`processGroup` stays a free string.** Content uses ~20 topic-specific phase labels (`handshake`, `searing`, …), not just the 4 mapped groups; unmapped values fall back to no state mapping.
- **Unknown keys are stripped, not rejected.** Zod's default object parsing drops unrecognised fields (e.g. `type: taxonomy-category` in category files), matching the old mappers. Alias *shapes* (wrapped files, `text:` for `prompt:`, top-level leaf fields, `event:` for `policy:`) were migrated out of the content instead.
- **`toSectionConfig` replaces `bundleToSections`.** The per-type switch is gone; a generic merge layers payload fields over section.md props. One documented exception: pillar-layer keeps the section.md title as its display title (its data carries a separate matrix title).
- **Failed sections cannot fail the topic.** `loadSection` catches storage errors and returns an error slot, so `loadOKFBundle` uses `Promise.all` over sections that never reject.
- **Runtime adapters may import composition.** `WebAppRuntimeAdapter` / `SingleHTMLEmbedAdapter` load bundles through `loadOKFBundle` (host → core, one-way). Storage adapters import nothing from composition, which is what removes the cycle.
- **Parity oracle.** Snapshots compare props with object keys sorted. Accepted differences after cut-over: `title: ""` → absent (8 intros; render-identical), unused `id` keys on hexagonal-architecture roadmap/challenge items dropped, `mtls/alternatives` gaining its 6 categories. Content fixes folded into the baseline: pixijs decision-tree prompts/leaves (previously rendered empty).
- **CLI coverage.** `okf:validate` validates every section folder on disk (linked or not) and fails on `index.md` links without a `section.md`.
