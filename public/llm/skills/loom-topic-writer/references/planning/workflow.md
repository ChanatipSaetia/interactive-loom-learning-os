## Shared authoring workflow (v6)

For a new topic or substantial redesign:

1. Identify the learner, goal, relevant source evidence and prior progress.
2. Discover compact capabilities. Map objective → knowledge structure → learner action → candidate views/interactions → representation and configuration; compare fidelity, perspective coverage, clarity, assessment fit and modeling feasibility. Compare OpenUI tables, cards, diagrams and charts as normal candidates, not only when no native type fits. Keep Bullets for genuine list tasks. Choose the clearest faithful combination, not the cheapest syntax; no ranking or quota. Compare only relevant candidate compositions; read their capability references progressively rather than loading every component. Distinguish presenting, exploring and assessing; each additional page must serve a distinct learner action. Read the installed mental-model and visual-planning references; with MCP start at read_reference({path:"index.md"}).
3. Use a schemaVersion 1 TopicPlan: topicId, goal, objectives (id, description, optional prerequisiteIds/evidenceOfLearning), and sections (id, title, objectiveRefs, components, activity, optional rationale/evidenceRefs/presentation/assessment). activity is the concrete learner action; explain the representation choice in rationale for new plans, including why relevant alternatives fit less well and any evidence or modeling limits. Use existing rationale, evidenceRefs, presentation and assessment fields; do not invent extra plan fields. A page is a compositional learning unit. components is required and lists the main visual/activity and supporting components from one shared catalog; representation and library are not plan fields. Do not choose a section type or library. Multiple components may cooperate in one learning activity. Every section is root = Page("Title", body, heading?). presentation names target read/present/both and strategy; assessment binds itemRefs to a successCriterion. Record a primary Flowchart view and any narration view transitions in presentation.strategy; for OpenUI name its intended table, cards, chart, Steps or diagram. For Text, name the prose-specific need and why structured candidates fit less well; generic clarity, simplicity or length is not a selection rationale. Keep objective and evidence references consistent; each section needs a distinct contribution.
4. Check objective coverage, prerequisites, supported representations, component availability and declared evidence links before writing OUI. Inspect advisory experience-readiness diagnostics too; resolve them or explicitly justify proceeding. Structural validity is not a judgment of teaching quality. Use validate_topic_plan if available; otherwise check the same contract locally and state which checks ran.
5. Load the selected section rules, then only the component contracts needed. Focused OpenUI requests include compact section rules and beats; list all actual composition components, while specific model dependencies are included and generic child alternatives remain choices. Use the full guide for extra examples when needed. Retrieve components by canonical name; LessonText and LearningGallery name the Loom-specific components. Read selected section references and only the relevant OpenUI families. With MCP, use read_reference for the selected components/<Name>.md paths.
6. Write OUI and narration from the checked plan, preserving IDs and exact signatures. Each virtual file requires exactly one root assignment: root = Topic(...) for the manifest, root = Page(...) for a page and root = Narration(...) for narration. Bare calls are not complete source. Use current buffers and targeted dependencies for edits.
7. Check each virtual file for its named root and correct document role, then use the existing OUI/narration compiler checks and compare the artifact with the plan, and measure Read/Present at phone/tablet widths when possible. Inspect clipping, fonts, reachable scroll content and narration focus. Repair only affected statements; report checks not run. Compiler validity and section variety are not teaching-quality scores.
8. Show the checked topic and save its exact source through the existing authorized storage workflow. Showing is not a confirmed save. Follow the skill output-location and validation references; provide the actual files.

For a small edit, read affected current source, preserve the existing learning decision, retrieve scoped contracts only as needed, validate and deliver the targeted change. Do not require every tool, a whole-guide reload or a new plan for each minor edit. Assistants own research, reasoning, generation and repair; Loom supplies deterministic contracts and checks.
