## Context

After #121–#126 a topic can be scaffolded (`okf:new`), autocompleted (`schemas/` + `.vscode/settings.json`) and validated (`okf:validate`). Humans and agents still follow different paths, though:

| Gap | Where |
|---|---|
| The AI skill predates the scaffold and never mentions `okf:new` | `.opencode/skills/create-topic-and-hexmap/SKILL.md` |
| The skill duplicates the doc instead of pointing to it, and only OpenCode discovers it | `.opencode/skills/` |
| Design intent (tracks, key items, boss) lives only in the author's head | `okf:new` flags take a flat section-type list |
| `okf:new` takes each section type once and refuses to touch an existing topic | `scripts/okf-new.ts` |
| Assessment grounding is prose-only and can't be checked | `AGENTS.md`, `docs/creating-topics.md` |
| Category/title/tags are duplicated in root `index.md` and `<topic>/index.yaml` | `public/okf/` |
| The campaign page only shows hard-coded topics | `KNOWN_HEXMAP_TOPIC_IDS` in `useGamificationCampaign.ts:22` |
| Validation passes silently when a topic is unregistered, has no hex map, has a bad roadmap `sectionId`, or has the wrong number of tracks | `scripts/validate-okf.ts` |

## Q1: Single Entry Point

**Q:** What single entry point should humans and AI both use to start a topic?

**A:** A brief file, then `okf:new`.

**Decision:** The author writes a topic brief first. `okf:new --from <brief>` scaffolds everything from it. The flag-based form stays as a shortcut that writes a brief.

## Q2: Canonical Flow Location

**Q:** Where is the flow written down so the human doc and the AI skill can't drift?

**A:** The doc is the source; the skill points to it.

**Decision:** `docs/creating-topics.md` §Quick start owns the flow. Agent skills are thin wrappers ("follow docs/creating-topics.md §Quick start") plus agent-only tips (e.g. Playwright MCP for the smoke check).

## Q3: Done Gate

**Q:** What gate must a topic pass, identically for humans and AI?

**A:** `okf:validate` passes, including new topic-level checks, and the grounding checklist is complete.

**Decision:** `okf:validate` gains these checks:
- the topic is registered
- the hex map exists
- roadmap `sectionId`s resolve
- the hex map has 2–4 tracks from the capital
- the campaign can discover the topic
- the brief matches the files on disk
- `groundedIn` refs are valid

Grounding is recorded per item (Q9). No automated text-similarity check, and the browser smoke check isn't part of the gate.

## Q4: Agent Discovery

**Q:** Which agents must discover the flow?

**A:** Any agent via `AGENTS.md`, plus OpenCode and Claude Code.

**Decision:** `AGENTS.md` points to the doc's flow. OpenCode keeps `.opencode/skills/create-topic-and-hexmap/` and Claude Code gets `.claude/skills/create-topic-and-hexmap/`. Both are thin wrappers pointing to the doc (one file symlinked or kept byte-identical). The Ralph loop isn't required to support it.

## Q5: Brief Location & Lifetime

**Q:** Where does the brief live, and does it survive scaffolding?

**A:** In the topic folder, committed.

**Decision:** `public/okf/<topic-id>/brief.yaml` is the permanent design record. Section loaders ignore it: it sits at the topic root, not under `sections/`.

## Q6: Brief Scope

**Q:** How much design does the brief capture?

**A:** Structure plus teach points.

**Decision:** The brief contains:
- meta (title, description, category, tags)
- 2–4 tracks
- each section as `{ name, type, title }`, so names are free and one type can appear more than once
- which sections drop key items
- the boss failure mode
- a `teaches:` list of `{ id, point }` per section

The brief gets a Zod schema and a generated JSON Schema, so it has autocomplete like other OKF files.

## Q7: Re-running the Scaffold

**Q:** Can `okf:new` be re-run against an evolving brief?

**A:** Yes, additively.

**Decision:** Re-running creates only missing section folders, registration and hex nodes. It never overwrites existing content files. The same command is used on day 1 and day 30. The current "refuses if the topic exists" behaviour becomes "adds only what's missing".

## Q8: Hex Map Authorship

**Q:** Who owns the hex map's layout and story?

**A:** Generated from the brief, then edited.

**Decision:** `okf:new` lays the tracks out radiating from the capital and places key items and the boss per the brief. The author then rewrites names and lore. Additive re-runs append nodes for new sections and never move existing ones.

## Q9: Grounding Record

**Q:** How do humans and AI prove grounding the same way?

**A:** A reference from each item to a teach point.

**Decision:** Each `quiz` question and `reflection-sequence` item carries `groundedIn: <teach-id>`. Tier 3 checks that the id exists in the brief's `teaches` for the prerequisite section. The author, human or AI, still confirms the section content actually teaches it.

## Q10: Brief ↔ Disk Drift

**Q:** What happens when the brief and the files on disk disagree?

**A:** Validation fails.

**Decision:** `okf:validate` fails in both directions: every section folder must be in the brief, and every brief section must have a folder. `fixHint`: update the brief and re-run `okf:new`.

## Q11: Metadata Ownership

**Q:** What is the single source for category, title and tags?

**A:** The brief; the other files are generated.

**Decision:** `brief.yaml` owns meta. `okf:new` writes `index.yaml` and the root `public/okf/index.md` link from it, and the validator flags mismatches.

## Q12: Campaign Discovery

**Q:** How does the campaign page find hex maps?

**A:** From the manifest or filesystem.

**Decision:** Delete `KNOWN_HEXMAP_TOPIC_IDS`. Any registered topic with `public/hexmaps/<id>.yaml` appears on the campaign page, so the flow has no extra step.

## Q13: Existing Topics

**Q:** What about the ~21 topics that have no brief?

**A:** A backfill script, with grounding strictness opted into per section.

**Decision:** `okf:brief --from-topic <id>` generates a brief from the existing files, with `teaches` left empty. Brief/drift checks apply to every topic once backfilled. `groundedIn` becomes required only once the prerequisite section lists `teaches`, so grounding migrates topic by topic.

## Q14: Brief Review Checkpoint

**Q:** Is there an approval point between the brief and the content?

**A:** Yes, a brief review, the same for both.

**Decision:**
- The flow step is: write the brief → `okf:validate --brief` → review → scaffold and fill.
- A human self-reviews. An AI stops and asks the user to approve the brief.

## Q15: Grounded Section Types

**Q:** Which types must carry `groundedIn`?

**A:** `quiz` and `reflection-sequence`.

**Decision:** Exactly the types named by the grounding rule in `AGENTS.md`.

## Q16: Generated File Sync

**Q:** How do generated files stay in sync with the brief?

**A:** They're committed, and `okf:new` re-syncs them.

**Decision:** `index.yaml` and the root link are committed files that `okf:new` rewrites. The validator fails on mismatch. Loaders and the app stay unchanged.

## Resulting Flow (identical for human and AI)

1. **Brief** — write `public/okf/<id>/brief.yaml` (or `okf:new <id> --category … --sections …` to get a starter brief).
2. **Check brief** — `npm run okf:validate -- --topic=<id> --brief`.
3. **Review** — a human self-reviews; an AI stops and gets user approval.
4. **Scaffold** — `npm run okf:new -- --from public/okf/<id>/brief.yaml` (additive; safe to re-run).
5. **Fill** — replace stub content, add `groundedIn` to every quiz and reflection-sequence item, and rewrite the hex map lore.
6. **Gate** — `npm run okf:validate -- --topic=<id>` passes, and each `groundedIn` has been confirmed against the section text.

To add a section later: edit the brief, then repeat from step 2.

## Implementation Slices

1. **Brief schema** — Zod `TopicBriefSchema` plus generated JSON Schema and a `.vscode` mapping; `okf:validate --brief`.
2. **`okf:new --from`** — scaffold from the brief with section names decoupled from types; additive re-run; generate `index.yaml`, the root link and a track-based hex map.
3. **Topic-level validator checks** — registration, hex map exists, roadmap `sectionId`, 2–4 tracks, brief ↔ disk drift, meta mismatch.
4. **`groundedIn`** — add to the quiz and reflection-sequence schemas (strict input stays idempotent); Tier 3 teach-ref check, required only when the prerequisite section has `teaches`.
5. **Campaign discovery** — remove `KNOWN_HEXMAP_TOPIC_IDS`; discover maps from the manifest or filesystem.
6. **Backfill** — `okf:brief --from-topic <id>`; run it for all existing topics.
7. **Docs & skills** — rewrite §Quick start around the 6-step flow; slim the OpenCode skill to a pointer; add the Claude Code skill; update `AGENTS.md`.

## Implementation Decisions (2026-09-27)

- **Prerequisite = any earlier section in the same track.** `groundedIn` may reference a `teaches` id of any section that comes before the assessment in its track (`prerequisiteTeachIds`).
- **The flag form of `okf:new` writes only a starter brief** (two tracks: first half and second half of `--sections`, with the last section of each as a key item). It does not scaffold, so the brief review in step 3 cannot be skipped.
- **The brief lives in the Validation Gateway**: `src/core/learning-engine/validation/topic-brief.ts` (`TopicBriefSchema`, `validateTopicBrief`, `validateTopicAgainstBrief`). It has zero React imports, and the CLI and scaffold share it.
- **Brief checks run only for topics with a `brief.yaml`** until the backfill (slice 6) lands.
- **Done:** slices 1, 2, 4 and 7, plus the slice-3 checks for topics with a brief. **Open:** slice 5 (campaign discovery), slice 6 (backfill), and slice-3 checks for topics without a brief.

## Parked Risks

- **`brief.yaml` is served publicly** from `public/`. That's harmless (design notes only), but `teaches` would be visible to learners who go looking.
- **Additive hex-map re-runs** may be unable to place a new node adjacent to its track without moving others. A fallback rule is needed: append at the track tip, or fail with a `fixHint`.
- **A flag-only `okf:new`** now writes a brief first; existing docs and tests for the flag form need updating.
